## 2. Parcours exact des données

1. `SceneService.saveScene` écrit un `SaveFileFormat` via `JsonArtemisSerializer` avec `setUsePrototypes(true)`, après retrait temporaire de l'état volatil. Les champs à défaut peuvent manquer dans un composant présent par son archétype. Source : S `service/SceneService.java:971-990,1231-1252`.
2. `RuntimeExport.exportPrepared` recrée `pixscape-project/`, convertit les métadonnées et disponibilité Studio, filtre les composants Studio dans la scène Artemis, copie atlas terminés/pages, effets, shaders, audio et Game Objects, génère les trois registres et prépare le HUD avant `project.json`. Source : S `configuration/RuntimeExport.java:109-253,636-744,778-854`.
3. `RuntimeProjectIO` lit `project.json`, initialise les registres ; `SceneAvailabilityPlan` demande scène et atlas, puis effets référencés/déclarés, Game Objects disponibles et union des HUD. Les chemins partent du **dossier passé à l'engine**. Source : R `loading/RuntimeProjectIO.java:47-177,199-340` ; `loading/SceneAvailabilityPlan.java:59-125,222-266`.
4. `SceneLoader` valide dans un monde Artemis temporaire, charge dans le monde actif, puis l'engine reconstruit dense Tiled, hiérarchies, transformations effectives, index d'atlas, HUD, rendu et Box2D. Source : R `loading/SceneLoader.java:40-169,171-270` ; `engine/PixscapeEngine.java:1398-1468,1610-1866`.

`project.json` a `projectFileName` (chaîne non blanche requise), `version`, `projectKind` (Studio écrit `pixscape-runtime-project` ; lecteur ne le vérifie pas explicitement), `runtimeRootDir`, `scenesDir`, `atlasesDir`, `effectsDir`, `animationsDir`, `shadersDir`, `audioDir`, `gameObjectsDir`, `scenes`, `currentSceneName`, `glSamples`. Les noms de dossiers absents/blancs reprennent les conventions ; `glSamples` hors 0/2/4/8 devient 0. `currentSceneName` absent/invalide est choisi. `sceneTag` vient du basename de `file` sans extension, pas nécessairement du nom humain de scène. R `loading/RuntimeProjectIO.java:47-105` ; `configuration/RuntimeConfig.java:118-190`.

Chaque `scenes.<clé>` a `sceneSchemaVersion=3`, `name` (défaut clé), `file` (non blanc, basename), `defaultHudScreenId` (chaîne logique ou null), `nextEntityStableId` et `nextPhysicsShapeId` (entiers positifs requis, au-dessus des IDs présents), `physicsEnabled` (false), `pixelsPerMeter` (100 si absent/non positif), `gravityX/Y` (0/-9,81), `doSleep` (true), `physicsParallaxX/Y` (`NaN` par défaut), `ambientMulR/G/B` (1) et `runtimeAvailability`. D `assets/pixscape-project/project.json:24-25,54-55` ; R `system/LayerStateBuildSystem.java:48-73`. `runtimeRootDir` conserve le chemin absolu de l'export si non blanc (ici un chemin local), mais les usages de résolution identifiés passent par `runtimeProjectDir` effectivement fourni. ## 3. Enveloppe Artemis, valeurs et identifiants

`JsonArtemisSerializer` écrit `metadata` (`version:1` observée), `componentIdentifiers` (objet **FQCN Java → alias court propre au document**), `entities` (objet clé = ID Artemis sérialisé), `archetypes` (objet ID → tableau d'alias). Une entité contient `archetype` entier et `components` objet alias → données. L'ensemble de composants effectif vient de **l'archétype** même si `components` omet un composant à valeurs par défaut. `{}` ne veut pas dire que les propriétés sont interdites. Un lecteur tiers peut interpréter les FQCN comme identifiants ; leur présence n'est pas en soi un défaut de portabilité. Les alias doivent être résolus **pour chaque fichier**, jamais figés globalement. D `assets/pixscape-project/scenes/scene1.json:1-43` ; R `loading/SceneLoader.java:58-69`.

Les IDs Artemis appartiennent au monde chargé. Les `aEid/bEid` des joints et `joint1Eid/joint2Eid` des gears sont `@EntityId` et remappés par Artemis. Ils sont distincts des `PixscapeIdentityComponent.stableId` durables de la scène, `physicsShapeId` avec son high-water, `SpatialBlockData.id/structureId` locaux à une map, et `sourceEntityId/jointLocalId` locaux à un `.gameobject`. R `component/physics/PhysicsJointComponent.java:33-39`, `PhysicsGearJointComponent.java:10-16` ; test `src/test/java/games/pixscape/runtime/loading/PhysicsJointSerializationRemapTest.java`.

Les `IntArray` et `ByteArray` LibGDX observés sont `{"items":[...],"size":n}` ; seuls les `size` premiers éléments sont actifs. Les autres sont capacité inutilisée. Les `Array<T>` de blocs et formes physiques sont des tableaux JSON directs, de même que les `float[]`. D `assets/pixscape-project/scenes/scene1.json:60-80,480-535`.

**Canonique contre tolérances.** Projet `"1"`, scène 3, Game Object 3, HUD screen 1, document HUD 2 et profil tileset 1 sont les versions acceptées ; aucune migration générale n'est trouvée. `TiledLayerComponent` complète les anciens `tileTransformFlags` absents dans une map de schéma 3 (R `component/TiledLayerComponent.java:44-59`). `null` et absence ne sont pas équivalents : `defaultHudScreenId:null` et plusieurs payloads Game Object nuls sont canoniques ; `CustomPropertiesComponent.properties=null` est rejeté. Les champs inconnus de `project.json` sont ignorés par sa lecture manuelle ; les codecs Game Object et HUD ont `setIgnoreUnknownFields(false)`. **Le comportement des champs ou composants inconnus dans Artemis 2.3.0 n'a pas été prouvé** ; ne promettre ni préservation ni rejet silencieux. Quatre cas `null` précis restent à tester : `TransformComponent.scaleX/Y`, `AnimationComponent.animationAssetIds`, `VisibilityComponent.visible` et `IntArray.items`. R `loading/RuntimeProjectIO.java:47-105`, `loading/SceneLoader.java:93-169`, `gameobject/GameObjectAssetLoader.java:450-460`, `hud/document/HudDocumentCodec.java:109-113`.

## 5. Sémantique de reconstruction

**Layer et ordre.** `LayerComponent` n'appartient qu'aux entités layer ; `EntityIndexComponent` porte layer/z locaux du contenu. `ContentLayerValidator` rejette leur double présence et l'ancien champ `LayerComponent.type` ; les fabriques Runtime créent `EntityIndexComponent` pour le contenu. `renderOrder().set(layer,z)` rejette le membre Game Object, tandis que `zIndex` sur lui modifie son z local ; la layer effective vient de la racine. Le Runtime compose ordre, visibilité et transformations hiérarchiques ; ne pas sérialiser l'ordre effectif calculé comme second champ. `SortKey64` classe layer, z, passe et tie, avec un mode d'ordre matériau pour mélanges opaques/commutatifs. R `loading/ContentLayerValidator.java:14-52`, `api/PixscapeApiImpl.java:525-576,1050-1180`, `system/GameObjectHierarchySystem.java:305-384`, `render/SortKey64.java:8-113`.

**Mise à jour ciblée du 29 septembre 2026 (postérieure à cet audit).** Le contrôle JSON préalable de `SceneLoader` recherche la double présence dans `entities.*.components` explicites et le champ `type` d'un objet Layer explicite. `SceneLoader` appelle désormais le même `ContentLayerValidator` après matérialisation des archétypes dans son monde temporaire, qui ne contient que la scène candidate, avant toute modification du monde appelant. Le parcours Engine conserve son contrôle de monde lors de la préparation via `TiledMapOwnership.validateWorld` ; Studio l'appelle à la sauvegarde. Les tests ciblés couvrent la combinaison héritée de l'archétype, y compris lorsque seul un payload est explicite. R `loading/ContentLayerValidator.java`, `loading/SceneLoader.java`, `tiled/TiledMapOwnership.java`, `engine/PixscapeEngine.java` ; S `service/SceneService.java`.

**Axes, origines et projection.** Positions/dimensions sont des unités Pixscape de rendu, transform rotation en radians ; l'origine de racine Game Object intervient dans sa matrice et les membres sont composés localement. ORTHO place par `origin + index × tileWidth/tileHeight` ; ISO combine deux coordonnées de grille avec demi-largeur et demi-hauteur. `angleDegrees` physique, `rotationDeg/coneAngleDeg` lumière sont des degrés. `pixelsPerMeter` convertit vers Box2D. R `system/GameObjectHierarchySystem.java:305-384`, `tiled/TiledMapLayerData.java:155-179`, `physics/PhysicsGeometryData.java`.

**Altitude.** `TiledLayerComponent.defaultTileAltitude/Height` sont des défauts **de map**. Une tuile utilise son altitude/hauteur propre lorsque `tileSpatialOverrides` indique un override ; sinon les tableaux clairsemés à 0 ne remplacent pas ces défauts. Un `SpatialBlockData` a sa propre altitude et sa hauteur par défaut 128, distinctes des tuiles. Les flags light/shadow de blocs sont des métadonnées : ni futures ombres ni future physique 2.5D ne font partie du contrat courant. R `component/TiledLayerComponent.java:17-105`, `tiled/TiledMapLayerData.java:384-405`, `spatial/SpatialBlockData.java:10-33`.

**Game Object : définition / instance.** `.gameobject` v3 a `rootSourceEntityId`, `entities` à IDs/parents locaux et `joints` locaux. Racine unique à `transform.x=y=0` et `entityIndex.zIndex=0` ; `entityIndex.layerIndex` et `LayerComponent` interdits. **`originX/Y`, `rotationRad` et `scaleX/Y` de racine restent sérialisés** : le loader ne les force pas à 0/1. Pour un parent Game Object, scale fini, positif et uniforme ; rotation finie permise. Les membres gardent transforms et z locaux. `spawn(asset,x,y)` affecte **exactement** x/y à la racine, met layer=0 sur les nouveaux `EntityIndexComponent`, remappe stable IDs, propriétés OBJECT et joints ; l'application fixe la layer/z d'instance. Les anciens alias `root(name,x,y)` et `requireRoot(name,x,y)` ne sont plus dans l'API. R `gameobject/GameObjectAsset.java:12-84`, `GameObjectAssetLoader.java:62-163`, `GameObjectRuntimeFragmentSpawner.java:57-89,299-347` ; S `service/gameobject/GameObjectAssetService.java:479-533,964-980`.

Une entrée d'asset `entities[]` sérialise `sourceEntityId` (i), `parentSourceEntityId` (i, -1 pour la racine), `transform{x,y,rotationRad,scaleX,scaleY,originX,originY}` (n), `entityIndex{zIndex}` (i local), puis les payloads facultatifs `meta.kind`, `identity.name`, `tags.values`, `customProperties`, `visibility.visible`, `boundsFlags.hasAabb/hasObb`, `dimensions`, `quadDeform`, `renderMaterial`, `assetRef`, `tint`, `animation`, `shaderParams`, `repeat`, `pointLight`, `coneLight`, `spatialHeight`, `physicsBody`, `physicsShapes[]` et `gameObject{}`. Le writer actuel émet souvent `null` pour les payloads absents et `[]` pour les formes/joints vides. `TransformData` Java initialise ses floats à zéro : scale doit donc être explicitement positif sur les parents pour passer la validation ; ne pas lui appliquer par analogie le défaut 1 du `TransformComponent` de scène. Les formes physiques ont des `localShapeId`, pas des `physicsShapeId` de scène ; les joints ont `jointLocalId` et deux body IDs locaux, avec payload typé (`distance/revolute/prismatic/pulley/gear/wheel/weld/friction/motor`). R `gameobject/GameObjectAsset.java:24-177`, `GameObjectAssetLoader.java:62-163` ; D `assets/pixscape-project/gameobjects/snake.gameobject:1-95`.

**Physique, atlas, HUD et code applicatif.** `physicsEnabled=false` exclut corps/formes/joints authored ; Box2D se construit des composants si actif. Les joints sont remappés puis créés ; les IDs de forme restent séparés. L'asset visuel est résolu par suffixe de région `__a<ID>` dans l'atlas de **la scène**, avec frames ordonnées par `index`. Le HUD est un environnement/passe distinct, avec hiérarchie Scene2D, layouts FREE/Table, styles intégrés ou Skin et actions `SHOW/HIDE`. Une application indépendante doit fournir caméra/viewport/zoom, choix de scène, systèmes gameplay et routage d'entrée vers le HUD ; ces éléments ne sont pas entièrement dans la scène. R `loading/SceneLoader.java:220-320`, `service/AtlasAssetIndexBuilder.java:27-125`, `hud/SceneHudFiles.java:44-123`, `hud/document/HudNode.java:5-66`, `engine/PixscapeEngine.java:546-581,747-790`.

Le document HUD v2 a `schemaVersion` et `root` ; chaque `HudNode` a `id`, `kind`, `actor.width/height`, visibilité initiale, payload de widget, `children` ordonnés ou `table`. Une taille d'acteur à 0 laisse Scene2D calculer sa taille naturelle. Un `HudChild` choisit `DIRECT`, `CELL` ou `FREE` ; en FREE, les ancres horizontale/verticale choisissent un point du parent, `pivotX/Y` un point normalisé de l'enfant (0 à 1), puis `offsetX/Y` ajoutent un déplacement en unités HUD. `HudSession` utilise `ScreenViewport`, une unité logique par pixel de viewport, et recalcule la surface/layout au resize. Les actions de fenêtre visent le `targetId` d'un nœud WINDOW/DIALOG. Styles intégrés sont des valeurs du Runtime ; `styleName`, `fontAssetId`, `image` et Skin externes exigent la fermeture des ressources. R `hud/document/HudDocumentV1.java`, `HudNode.java`, `HudActorProperties.java`, `HudChild.java`, `HudFreePlacement.java`, `HudWindowAction.java` ; `hud/HudSession.java:20-51,95-105,210-218`.

## 8. Plan des schémas et validations

**Emplacement proposé :** `pixscape-runtime/docs/schemas/<release>/`, avec publication sous `pixscape-site/public/schemas/pixscape/<release>/` après choix du tag. Employer `$schema: https://json-schema.org/draft/2020-12/schema` ([spécification JSON Schema](https://json-schema.org/specification)). Le site Astro actuel n'a pas de validateur JSON Schema dans `package.json` ; choisir/verrouiller un outil compatible 2020-12 à l'implémentation. Les schémas et fixtures doivent rester près du producteur/lecteur, puis être distribués en copie versionnée sur le site.

| Fichier proposé | Contenu |
|---|---|
| `project.schema.json` | Projet, scènes, versions, disponibilités, champs obligatoires et defaults documentés ; `projectKind` canonique sans prétendre qu'il est validé aujourd'hui. |
| `scene-artemis.schema.json` | `metadata/componentIdentifiers/entities/archetypes`, entrées d'entités, clés d'IDs et relation alias/archétypes. |
| `scene-components.schema.json` | Définitions de tous les composants de section 4, joints typés, maps, Spatial, properties et composants vides. Discriminant par FQCN ; **pas d'alias court universel**. |
| `common.schema.json` | `IntArray`/`ByteArray`, couleurs RGBA8888, identités, coordonnées, propriétés typées, sentinelle `"NaN"` ciblée. |
| `gameobject-v3.schema.json` | Asset local, racine, entités, joints et unions de payloads. |
| `hudscreen-v1.schema.json` ; `hud-document-v2.schema.json` | Asset HUD puis hiérarchie de nœuds, kind/payload, placements, Table, styles, actions et références. |
| `animations.schema.json` ; `tiled-animations-v1.schema.json` ; `tileset-profiles-v1.schema.json` | Registres et profils, sans inventer de version pour `animations.json`. |

**JSON Schema** couvre types, clés locales, enums, versions, bornes, ``required` réellement nécessaires et ``oneOf` pour payloads. **Code sémantique** doit résoudre FQCN↔alias dans chaque document, comparer archétypes/entités, vérifier fichiers/pages, unicité/high-water/portée des IDs, parents et cycles, absence de layer+index, layer existante et ordre effectif, alignement `items/size` et maps, fermeture atlas/animations/profils/HUD/particules/Game Objects, géométrie Box2D, styles, ainsi que l'écart Spatial documenté. Un schéma ne démontre ni la concordance source/export ni l'identité du rendu.

**Questions nommées avant de marquer les schémas normatifs :** comportement d'Artemis 2.3.0 devant champ/composant FQCN inconnu ; `null` explicite pour `Transform.scaleX/Y`, `Animation.animationAssetIds`, `Visibility.visible` et `IntArray.items` ; statut canonique des caches AABB/OBB/flags de vue ; politique sur `linkedTileRefs.tileAssetId` historique ; composants d'extension autorisés lors d'une future exportation. Le contrat actuel peut être documenté sans modifier le format pour répondre à ces questions.
