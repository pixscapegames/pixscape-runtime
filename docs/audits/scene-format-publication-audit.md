# Audit de publication du format de scène Pixscape

État audité : 28 septembre 2026. `pixscape-runtime` : branche `develop`, commit `9013139511cf023805507a4e409f8d39598f944e` ; `pixscape-studio-free` : branche `develop`, commit `3fc9bb3ede34e929567bb074b699a697bd334443`. `git status --short --branch` ne signalait aucune modification locale dans ces deux dépôts avant cet audit. `tiled-iso-demo` : branche `main`, commit `d9e8c07da70784e80fbdc81180330870e0ffa856`, avec des modifications et suppressions suivies ainsi que de nouveaux fichiers non suivis dans `studio/` et `assets/pixscape-project/` ; **tout l'état local actuel** est pris en compte, sans réinitialisation. Les deux `AGENTS.md` de Runtime/Studio renvoient aux profils centraux `runtime` et `studio-free` ; aucun `AGENTS.md` applicable n'a été trouvé dans la démo. Dans les références ci-dessous, **R** signifie `pixscape-runtime/src/main/java/games/pixscape/runtime/`, **S** signifie `pixscape-studio-free/src/main/java/games/pixscape/studio/`, **D** signifie la racine de `tiled-iso-demo/` ; **RT** et **ST** désignent les racines de tests Runtime et Studio. Une référence `fichier:ligne` est relative à l'une de ces racines.

## 1. Résumé et statut

**Fait vérifié.** L'unité chargeable est un répertoire `pixscape-project` contenant `project.json`, un fichier `scenes/<nom>.json` désigné par les métadonnées, et l'atlas `atlases/<nom>.atlas` avec ses pages. Le Runtime charge d'abord la configuration et les registres, acquiert la scène et ses ressources, désérialise le monde Artemis, puis construit les caches de cartes, les registres, les rendus et la physique. Références : R `engine/PixscapeEngine.java:347-372`, `loading/SceneAvailabilityPlan.java:63-77`, `engine/PixscapeEngine.java:1398-1459`.

**Corpus réel trouvé.** `tiled-iso-demo` contient un projet source Studio et un export `assets/pixscape-project/` de deux scènes, avec atlas et HUD pour `demo`. Il donne des observations concrètes sur `JsonArtemisSerializer` : `metadata.version: 1`, `componentIdentifiers`, `entities`, `archetypes`, composants vides pour valeurs par défaut, et `IntArray` sous forme `{items,size}`. Les deux dépôts principaux n'incluent pas ce corpus dans leurs tests. Références : D `assets/pixscape-project/project.json:1-75`, `assets/pixscape-project/scenes/scene1.json:1-80`, `assets/pixscape-project/scenes/scene44.json:1-65`, `assets/pixscape-project/hud/test3.json:1-13`.

**Conclusion.** L'export de la démo est un candidat de validation réel, mais il est en décalage avec son projet source et utilise une application liée à Runtime `0.1.11`, contre `0.2.2` dans les dépôts audités. Il faut l'ouvrir et le réexporter avec Studio actuel, puis tester son chargement avec Runtime actuel avant d'en faire un exemple normatif. L'audit reste une cartographie du contrat et de ses lacunes, **pas encore une spécification suffisante pour reconstruire toute scène sans lire le Runtime**. Références : D `gradle.properties:23-25`, `studio/tiled-iso-demo.json:43-78`, `assets/pixscape-project/project.json:41-70` ; `pixscape-studio-free/gradle.properties:14` ; `pixscape-runtime/gradle.properties:8-9`.

## 2. Parcours des données et distinction des états

1. Studio sauve `project.json` et la scène sous `scenes/`. `saveScene` sélectionne toutes les entités (ou les entités de contenu si demandé), installe `JsonArtemisSerializer` avec prototypes pour une écriture compacte, efface provisoirement l'état volatil puis écrit `SaveFileFormat`. Références : S `service/SceneService.java:971-990`, `service/SceneService.java:1231-1252`.
2. L'export recrée `pixscape-project`, dérive les métadonnées de scène, enlève des composants de l'AST JSON Artemis et réécrit la scène. Il copie les atlas, effets, shaders, audio et Game Objects, produit les registres d'animation et de profils de tilesets, prépare le HUD puis écrit `project.json`. Le format éditable et le format exporté **partagent l'enveloppe Artemis**, mais ne sont pas identiques : métadonnées distinctes et composants filtrés. Références : S `configuration/RuntimeExport.java:85-111`, `configuration/RuntimeExport.java:128-162`, `configuration/RuntimeExport.java:174-237`, `configuration/RuntimeExport.java:751-826`.
3. Le Runtime lit `project.json` avec `JsonReader`, applique les défauts et validations, charge `animations.json`, `tiled-animations.json` et `tileset-profiles.json` s'ils existent. Il acquiert ensuite la scène, l'atlas et les dépendances déclarées ou détectées. Références : R `loading/RuntimeProjectIO.java:47-105`, `loading/RuntimeProjectIO.java:108-197`, `loading/SceneAvailabilityPlan.java:63-77`, `loading/SceneAvailabilityPlan.java:222-266`.
4. `SceneLoader` vérifie la scène dans un monde Artemis séparé, puis la charge avec le même sérialiseur. Le Runtime reconstruit ensuite les données denses Tiled, les caches de transformation, les hiérarchies, l'atlas, les particules, les rendus et Box2D. Ces résultats sont **calculés au chargement**, pas des champs normatifs à exporter. Références : R `loading/SceneLoader.java:40-115`, `loading/SceneLoader.java:81-90`, `component/TiledLayerComponent.java:14-15`, `engine/PixscapeEngine.java:1417-1468`, `engine/PixscapeEngine.java:1610-1659`.

## 4. Contrat actuel vérifié

### Enveloppes, versions et valeurs

- `project.json` est un objet. Les propriétés lues sont `projectFileName`, `version`, `runtimeRootDir`, `scenesDir`, `atlasesDir`, `effectsDir`, `animationsDir`, `shadersDir`, `audioDir`, `gameObjectsDir`, `currentSceneName`, `glSamples` et l'objet `scenes`. `version` absent ou blanc devient `"1"`, seule version acceptée ; `projectFileName` est requis ; les répertoires blancs retrouvent leurs valeurs par défaut ; `glSamples` hors 0/2/4/8 devient 0 ; une scène courante absente peut être choisie automatiquement. Les clés inconnues ne sont pas parcourues par ce lecteur manuel. Références : R `loading/RuntimeProjectIO.java:47-72`, `configuration/RuntimeConfig.java:31-58`, `configuration/RuntimeConfig.java:118-190`.
- Chaque `scenes.<clé>` doit être un objet avec `sceneSchemaVersion` numérique égal à **3**, `nextEntityStableId` et `nextPhysicsShapeId` numériques positifs et un `file` non blanc. Les autres champs connus sont `name`, `defaultHudScreenId`, `physicsEnabled`, `pixelsPerMeter`, `gravityX`, `gravityY`, `doSleep`, `physicsParallaxX/Y`, `ambientMulR/G/B` et `runtimeAvailability` (Studio émet `sprites`, `animations`, `particles`, `gameObjects`, `tiledTiles`, `tiledAnimations`). Le lecteur de métadonnées n'extrait explicitement que les listes `particles` et `gameObjects` ; les autres servent à d'autres étapes ou restent à vérifier. Références : R `loading/SceneMetaRuntime.java:17-44`, `loading/SceneMetaRuntime.java:65-135`, `configuration/RuntimeConfig.java:143-173` ; S `configuration/RuntimeExport.java:681-744`.
- **Absent / null / vide / défaut :** pour les métadonnées, les getters avec défaut conservent généralement la valeur initiale si le champ est absent ; `file` absent ou blanc échoue ensuite ; disponibilité absente/non objet ou listes non tableaux donnent des listes vides pour particules et Game Objects ; un `defaultHudScreenId` vide est normalisé. `pixelsPerMeter <= 0` devient 100. Ne pas généraliser ces règles au JSON Artemis : la sortie compacte `setUsePrototypes(true)` peut omettre des champs, mais l'ensemble exact des omissions (et le traitement de `null` explicite) n'est pas prouvé par un fichier exporté représentatif. Références : R `loading/SceneMetaRuntime.java:65-105`, `configuration/RuntimeConfig.java:154-171` ; S `service/SceneService.java:1235-1249`.
- La scène est un `SaveFileFormat` de `JsonArtemisSerializer`. L'export de la démo montre les clés racine `metadata` (`version: 1`, version du sérialiseur distincte de `sceneSchemaVersion`), `componentIdentifiers` (FQCN → nom court), `entities` (clés numériques en chaînes, chacune avec `archetype` et `components`) et `archetypes` (ID → liste de composants). Un composant peut être dans l'archétype sans champs dans `components` ; `{}` signifie valeurs par défaut observées. Les `IntArray` comprennent `items` et `size`, et seuls les `size` premiers éléments sont actifs. Ces observations ne couvrent pas toutes les variantes de composants. Les classes Java dans `componentIdentifiers` constituent une difficulté de portabilité ; le filtre retire sept composants listés et les identifiants dont le FQCN contient `.studio.`, sans preuve que ce second critère retire toute occurrence dans `entities`/`archetypes`. Références : D `assets/pixscape-project/scenes/scene1.json:1-39`, `assets/pixscape-project/scenes/scene1.json:60-69`, `assets/pixscape-project/scenes/scene44.json:33-40` ; S `configuration/RuntimeExport.java:34-45`, `configuration/RuntimeExport.java:779-826`.
- Le Runtime valide la représentation finale de `LayerComponent` (champ `type` refusé), les propriétés personnalisées, identités stables, hiérarchie Game Object, schéma physique et configuration des maps avant le chargement réel. Il n'existe pas, dans ce chemin, de validation générale JSON Schema ni de migration automatique de la scène. Références : R `loading/SceneLoader.java:93-169`, `loading/SceneLoader.java:171-245`.

### Entités, hiérarchie et rendu

- `LayerComponent` contient `layerIndex` et `spatialEnabled`; `EntityIndexComponent` porte `layerIndex` et `zIndex` pour le contenu. `TransformComponent` stocke `x`, `y`, `originX/Y`, `rotationRad`, `scaleX/Y` ; cosinus, sinus et inverses sont transients. La hiérarchie associe l'enfant par `GameObjectMemberComponent.parentStableId` à `PixscapeIdentityComponent.stableId`, et le système compose les transformations locales, la visibilité et le Layer effectifs. Les valeurs numériques sont des unités de monde ; les angles des transforms sont en radians. Références : R `component/LayerComponent.java:5-7`, `component/EntityIndexComponent.java:5-7`, `component/TransformComponent.java:6-29`, `component/GameObjectMemberComponent.java:13-14`, `system/GameObjectHierarchySystem.java:238-250`, `system/GameObjectHierarchySystem.java:315-384`.
- Les références visuelles `AssetRefComponent.assetId` et `atlasTag` se résolvent dans l'atlas de scène ; `AnimationComponent` porte une liste d'IDs d'assets, `currentClip`, `fps`, `stateTime`, `playing`, `loop`, `frame`. `RenderMaterialComponent` stocke `shaderIdx` et `blendModeId` : reproduire un rendu identique implique les conventions des shaders et modes de mélange, pas seulement la géométrie JSON. Références : R `component/AssetRefComponent.java:9-21`, `component/AnimationComponent.java:6-21`, `component/RenderMaterialComponent.java:9-50`, `service/AtlasRuntimeService.java:160-216`.
- Une Map Tiled est une entité avec `TiledLayerComponent` et `EntityIndexComponent`. La projection est `ORTHO` ou `ISO`; dimensions, origine, `chunkSize` et tableaux clairsemés `tileXs`, `tileYs`, `tileAssetIds`, `tileTransformFlags` sont persistés ; `data` dense est transient. Au chargement, les flags manquants sont complétés puis les cellules sont posées dans la map calculée. La projection orthogonale utilise `origin + index × taille de tuile`; l'isométrique utilise les demi-largeur et demi-hauteur. Les hauteurs et flags Spatial existants décrivent le comportement actuel, sans prétendre annoncer une fonctionnalité future. Références : R `component/TiledLayerComponent.java:12-42`, `component/TiledLayerComponent.java:44-105`, `engine/PixscapeEngine.java:1610-1659`, `tiled/TiledMapLayerData.java:155-179`, `tiled/TiledProjection.java:4-6`.
- Les Game Objects déjà insérés dans une scène sont des **entités développées**, avec marqueur `GameObjectComponent.sourceAssetId` sur la racine et références `parentStableId` ; le chargement d'une scène ne déclenche pas automatiquement la réinstanciation du fichier source. L'asset `.gameobject` est chargé séparément pour un spawn : `schemaVersion: 3`, `rootSourceEntityId`, `entities` et `joints`, IDs locaux, racine unique, cycle interdit, puis allocation de nouveaux IDs stables à l'instanciation. Références : RT `loading/GameObjectSceneLoadingTest.java:25-58` ; R `gameobject/GameObjectAsset.java:12-53`, `gameobject/GameObjectAssetLoader.java:23-109`, `gameobject/GameObjectRuntimeFragmentSpawner.java:57-89`.

### Physique, propriétés et HUD

- La physique globale vient des métadonnées (`physicsEnabled`, `pixelsPerMeter`, gravité, sommeil) ; les corps et formes sont des composants de scène, les joints sont des entités indépendantes avec `PhysicsJointComponent.type`, `aEid`, `bEid` et ancres locales **en mètres**. Les types de corps sont les entiers 0/1/2 ; les types de joint 0 à 9. Les IDs Artemis référencés par les joints sont remappés par la sérialisation ; leur portée et leurs invariants doivent faire partie de la validation sémantique. Références : R `engine/PixscapeEngine.java:1817-1866`, `component/physics/PhysicsBodyComponent.java:8-22`, `component/physics/PhysicsJointComponent.java:14-56` ; RT `loading/PhysicsJointSerializationRemapTest.java:75`.
- Les propriétés personnalisées sont typées `STRING`, `BOOLEAN`, `INTEGER`, `FLOAT`, `COLOR`, `OBJECT`, `CLASS`. `OBJECT` porte un stable ID (`-1` = pas de cible) ; `COLOR` est un entier RGBA8888 ; `CLASS` porte un **nom de classe sous forme de chaîne** et des membres imbriqués. Le lecteur valide la structure, pas l'existence ni l'exécution d'une classe Java ainsi nommée. Aucune convention de script/behavior instanciée à partir de ces noms n'a été démontrée. Références : R `property/PropertyType.java:4-20`, `property/PropertyValue.java:64-95`, `property/PropertyValue.java:191-211`, `loading/SceneLoader.java:191-229`.
- `defaultHudScreenId` active éventuellement un asset `.hudscreen` v1, qui pointe par `documentId` vers un document JSON `schemaVersion: 2` avec un seul `root`. Les nœuds ont `id`, `kind`, propriétés d'acteur, payload selon le widget, `children` ordonnés ou disposition `table`. Le placement libre utilise ancrages, pivots et décalages ; les actions de boutons ciblent des IDs de nœuds de fenêtre/dialogue. Les skins, fontes et atlas sont résolus relativement au projet et matérialisés en Scene2D, ce qui exige une réimplémentation du comportement de layout, styles et input pour un runtime indépendant. Références : R `hud/HudScreenAsset.java:4-29`, `hud/HudScreenLoader.java:44-84`, `hud/document/HudDocumentV1.java:3-23`, `hud/document/HudNode.java:5-60`, `hud/document/HudChild.java:10-14`, `hud/document/HudFreePlacement.java:10-16`, `hud/document/HudWindowAction.java:3-13` ; RT `resources/games/pixscape/runtime/hud/document/v1/materializer-smoke.json:1-90`.
- La caméra du monde n'est pas reconstruite à partir d'un composant de scène Runtime : l'application fournit ou reçoit une `OrthographicCamera`; `resize` règle les dimensions de viewport. Position, zoom et politique de resize ne sont donc pas reproductibles à partir des seuls fichiers de scène. Références : R `engine/PixscapeEngine.java:546-581`, `engine/PixscapeEngine.java:680-689`, `engine/PixscapeEngine.java:764-781`.

## 6. Candidat réel : `tiled-iso-demo`

### 6.1 Projet source Studio (`studio/`)

**Faits vérifiés.** `studio/tiled-iso-demo.json` est un projet `pixscape-studio-project` version `"1"` avec deux scènes v3 : `demo` → `scenes/scene1.json`, et `Tutorial` → `scenes/scene44.json`. `demo` active la physique, déclare `hud/test3`, `Blood.p`, `Flame.p` et `gameobjects/snake.gameobject` ; `Tutorial` désactive la physique et n'a pas de HUD par défaut. ## 10. Limites et décisions à prendre

Cet audit **n'est pas complet** au sens d'une spécification indépendante exploitable : la démo apporte un export réel, mais non synchronisé avec son source et non chargé ici avec Runtime `0.2.2`. Elle permet de vérifier les omissions et `null` de **ses** composants, pas de tous les composants imbriqués, formats d'effets/skins/shaders ni du rendu comparé d'une scène complète. Le comportement du lecteur Artemis pour classes/champs inconnus et composants personnalisés, les cycles de ressources, les échecs tardifs de référence et les conventions détaillées de rendu Spatial restent à éprouver. Les fichiers TMX/TSX sont des sources d'import, et les sons/scripts n'ont pas été établis comme dépendances d'une scène sérialisée ; l'audio copié à l'export ne suffit pas à conclure à un contrat de son. Références de contrôle : D `studio/tiled-iso-demo.json:43-78`, `assets/pixscape-project/project.json:41-70`, `gradle.properties:24` ; S `configuration/RuntimeExport.java:174-237` ; R `loading/SceneLoader.java:93-115`.

Décisions nécessaires : sélectionner et autoriser les assets du corpus public ; fixer le périmètre des composants/custom properties pris en charge par un lecteur tiers ; définir la politique des champs inconnus et les erreurs de références ; figer les versions et les URL de release ; décider si les formats LibGDX externes sont inclus ou seulement référencés. **Fichier créé par cet audit :** `pixscape-runtime/docs/audits/scene-format-publication-audit.md`. **Autres fichiers créés ou modifiés : aucun.** Aucun schéma, commit, push ou déploiement.
